# Hosted Studio preview

The browser preview is live at [abstracteng.com/xmpos](https://abstracteng.com/xmpos/), with its [user manual](https://abstracteng.com/xmpos/manual/). The original preview was first published on 2026-11-09. This deployment contains the graphical browser application, original demo sounds and three explicitly approved CC0 test kit selections. It contains no Linux image, native executable, personal project, secret or hardware adapter.

Open the page on a phone or computer, tap **Enable audio**, then Play or a pad. Audio follows that browser's output. Keep the Studio tab visible; hiding it stops playback. Projects autosave on that browser and origin. Portable Save/Open project downloads are the way to move work between the Mac and phone; there is no account sync or project-upload backend. Loading or refreshing the site requires connectivity; a service worker/offline-installable PWA has not been added.

Device → Sample → REC can record from the browser microphone after permission is granted. Monitor defaults on; while playing, Record queues a four-bar loop for the next bar. Enable microphone permits monitoring between takes, and Choose WAV input supplies a file instead. The separate built-in Mac microphone helper in Studio remains local to the development server. The static host accepts only the bounded error and anonymous usage reports described below, refuses other write methods and returns a clear error for native recording endpoints. Physical MIDI, USB, Force/MPC deployment and hardware qualification remain unavailable.

## First visit and returning projects

A browser with no saved project loads **Night Shift**, the original 124 BPM house song, in both Device and Advanced Studio. Press **Play** to hear the complete arrangement; playback does not start automatically. The verified portable song is saved locally on first launch.

Any existing autosave takes precedence, including an intentionally empty new project. Once someone creates and works on another project, that autosaved work is what loads on return. A recovered previous save also takes precedence; corrupt or incompatible storage is retained rather than replaced with the starter. Another tab saving during the starter download is rechecked before writing, and the normal storage conflict guard remains active. New Project continues to create a blank project.

`npm run web:first-visit:test` exercises a fresh profile, Play output, New Project, automatic saving, reload, closing/reopening a tab and sharing the same saved project with Advanced Studio. The web packager checks that the pinned starter file is present and matches its size and SHA-256 before deployment.

## Build and deploy

The main Vite configuration supports two builds:

- `npm run build`: local/default origin, including the manual.
- `npm run web:build`: `/xmpos/` asset and navigation prefix, written to its own `dist-hosted/` folder. Local builds and `npm run check` rebuild `dist/` for `/` and never touch it. Preview it locally with `npx vite preview --mode hosted --host 127.0.0.1 --port 5174`, then open <http://127.0.0.1:5174/xmpos/>.

Use the Cloudflare CLI deployment project in `tools/web-host`, with its own pinned package lock. Its generated `.cloudflare` artifacts are ignored. Use a Node version supported by the pinned cf package (24.22 or later in Node 24 for new installs). Existing local build checks were also exercised with the workspace's Node 24.14 runtime.

```sh
npm run web:build
npm run web:prepare
npm ci --prefix tools/web-host
cd tools/web-host
npx cf deploy --dry-run
npx cf deploy --prebuilt
```

Authenticate using the existing account's normal Cloudflare CLI login or a suitable `CLOUDFLARE_API_TOKEN` in the environment. Never put credentials in this repository or command arguments. A deployment needs Worker/static asset and route access in the configured account and zone. Local deployment authentication is independent of the browser application's visitors.

The deployment CLI has its own login, separate from Wrangler. The previous Wrangler credential could read the account but failed deployment reads. A fresh `cf auth login --force --no-browser` device authorization, approved by the owner, resolved that failure. This deployment requested `user:read account:read workers:write workers_scripts:write workers_routes:write workers_deployments:read workers_observability:write zone:read` (plus OAuth refresh access). The CLI stores credentials outside the repository. Reuse that profile for subsequent deploys; a new browser approval is only needed if reauthentication becomes necessary. Device codes expire after five minutes and must not be reused after expiration.

## Usage analytics

The **hosted browser client only** sends anonymous, cumulative session snapshots to the same-origin `/xmpos/api/analytics/collect` endpoint. Local development, native Live sessions and the emulator do not send usage reports. The shared C++ UI exposes fixed action counters to the browser adapter; it exposes no action arguments, note values, names or audio. The adapter counts physical-panel buttons, mouse/touch and keyboard pad activations, Q-Link adjustments and screen taps. Feature actions identify touchscreen operations such as clip creation, saving, sampling, chopping, effects editing and undo. Actions are requests, rather than claims that an operation succeeded.

The [private usage dashboard](https://abstracteng.com/xmpos/analytics/) shows anonymous sessions, active/foreground time, playing and recording time, daily use, screens, feature actions, machine selections and controls by screen. It supports today, seven, thirty and ninety-day UTC session cohorts and CSV export. These are sessions, **not unique people**: IDs are random, kept in memory only, and change on reload or after thirty idle minutes. Idle visible tabs contribute to foreground time but stop contributing to active time after one minute without interaction unless transport/recording continues. Timing is approximate and final reports can be lost when a browser closes. Thirty-second snapshots, plus visibility/pagehide beacons, avoid a request for every interaction. Monotonically numbered snapshots make retries and out-of-order delivery idempotent.

No project/sample names, typed text, project IDs, files, musical note/velocity sequences, audio, referrers or persistent visitor identifiers are collected. The backend stores neither IP addresses nor user agents. Cloudflare's transient rate limiter uses the connection address to bound public endpoint requests; it does not write that address to the analytics database. The hosted client respects Do Not Track and Global Privacy Control. **Usage analytics** below the browser interface provides an opt-out, remembered locally and synchronized across tabs. It does not affect music controls. Session rows expire after ninety days and a daily scheduled Worker removes them. Dashboard reports return aggregates only, never session IDs; responses are uncached and require the private key.

Owner setup:

1. Use `npm run web:analytics:key` to create or reuse `artifacts/web-analytics/dashboard-key.txt`. This file and its deploy secret hash are ignored and have owner-only file permissions. Never copy the key to source, a URL or public assets. Paste it into the dashboard login; the dashboard keeps it only in tab memory. Preserve this file for subsequent deployments. Intentional key rotation requires creating a replacement locally and deploying its new hash.
2. The Cloudflare login must include `d1:write` in addition to the existing Worker deployment scopes. The existing account is used; no separate analytics vendor is involved. Create the `xmp-web-analytics` D1 database with the existing `cf` CLI, then apply `tools/web-host/migrations/0001_usage.sql` with `cf d1 migrations apply DATABASE_UUID --dir migrations` from `tools/web-host` (preview it with `--dry-run` first). Configuration binds the database by name.
3. Run `npm run web:analytics:test` for the hosted-bundle browser/Worker/SQLite end-to-end test. It checks feature and button collection, private dashboard authentication, CSV export, mobile layout, privacy preferences and resilience when the collector is offline. It uses an isolated local database and muted browser, without production visitor data or physical inputs.
4. Deploy the frozen hosted assets with `npm run web:build`, `npm run web:prepare`, then **`cf build`**, `cf deploy --prebuilt --dry-run` and `cf deploy --prebuilt --secrets-file ../../artifacts/web-analytics/secrets.json` from `tools/web-host`. Always rebuild the Cloudflare output after preparing assets, and compare staged files before publishing. Only a SHA-256 digest of the random dashboard key is deployed as a secret.

The collector strictly validates bounded payloads against a fixed vocabulary, uses prepared SQL, enforces same-origin JSON POSTs and rate limits requests. Reports require the key in an Authorization header. Analytics failures do not prevent XMP from starting or making sound. Database schema and Worker handler tests use real SQLite, including duplicate/out-of-order snapshots and retention checks. Primary API references: [D1 prepared statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/) and [Cloudflare typed bindings](https://developers.cloudflare.com/cf/projects/cloudflare-config/).
