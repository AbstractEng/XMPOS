# Porting XMP's core and the Live interface to C++

Decided by the owner on 2026-11-12: XMP's core moves to C++, shared by the browser (as WebAssembly) and the MPC Live (native), and the Live gets a full XMP interface on its own screen. The browser's interface stays in TypeScript (HTML and DOM).

## Why

- One implementation of the project model, sequencing and sound for both, so the Live plays the same projects the browser makes.
- Speed where it matters: the sound engine is about 3.5× faster in C++ and the performance window about 5.8×. Editing and loading projects are not time-critical; in the browser the gain there is consistency, not speed.

## Rules for the C++

- **Headers in `native/include/xmp/`:** each port has a parity test against the TypeScript it replaces, kept as a reference until the port has been in use for a while.
- **One toolchain:** the same headers build with the pinned Zig for WebAssembly and with the system or ARM compiler natively. The WebAssembly build has the C library only, no C++ standard library, so the core uses XMP's own small containers (`base.hpp`) and JSON (`json.hpp`) instead of `std::`.
- **Real-time code** (anything the audio thread calls) never allocates, locks or does I/O. The project model may allocate; it is never touched by the audio thread.
- **Bounded input:** every project and module input keeps the limits the TypeScript schemas enforce, with the same accept and reject decisions and the same messages for XMP's own checks.

## Phase 1 notes (2026-11-12)

- `base.hpp`: `Vec` and `Str` on `malloc`, with their own placement `new` and `move` (the WebAssembly toolchain has no C++ headers at all).
- `json.hpp`: reading and writing as `JSON.parse` and `JSON.stringify` do: key order (array-index keys first), shortest number text, escapes, lone surrogates (kept as WTF-8).
- [`tests/parity/json-parity.test.ts`](../tests/parity/json-parity.test.ts) compares it with JavaScript on 3,000 random documents (compact and indented), 20,000 random numbers (including random bit patterns, subnormals and the extremes) and 38 malformed or edge-case inputs. Output is byte-identical and the accept and reject decisions match. It also builds for WebAssembly (about 59 KB with `printf` and `strtod`) and gives the same output there.
- **Found by the test:** Node 24's `JSON.parse` can return the wrong name for a property whose name is a lone surrogate, after it has parsed other documents (a V8 key-cache bug). The C++ is correct. The test keeps such keys out of the comparison.

## Phase 2 notes (2026-11-13)

- **What it does:** `project::open(text)` does what the TypeScript's `parseProject` and `openProject` do:
  - the import preflight;
  - the JSON;
  - the schemas of versions 1 to 6;
  - every check of XMP's own (references, budgets, sequences, performance, mix, effects, machine state bounds, the built-in machines' states);
  - migration to version 6.

  The result is the canonical version 6 document. Its `JSON.stringify` is byte-identical to the TypeScript's.
- **The schemas** are built from a small checker (`project_schema.hpp`) with zod 4's semantics:
  - strict objects;
  - the schema's key order, with extended fields keeping their place;
  - safe integers and finite numbers;
  - records that drop `__proto__`, as zod does;
  - string lengths in code points. Zod 4 counts a surrogate pair once, unlike JavaScript's `.length`.
- **Decisions are identical.** Messages from the preflight, the version check and XMP's own checks use the TypeScript's words. For structural problems the C++ names the first problem (for example `project.tracks[5].name: text out of bounds or malformed`), where zod lists every issue as JSON.
- **Checks:**
  - [`tests/parity/project-parity.test.ts`](../tests/parity/project-parity.test.ts) runs 240 random rich projects (40 in each of versions 1 to 6) and 3,000 random mutations of them (missing and extra keys, wrong types, values at and beyond every limit, broken references, duplicates, real `__proto__` keys), plus the preflight and version rules.
  - Five deliberate faults in the C++ each fail it: a dropped check, a name limit off by one, two keys swapped, a wrong migration default, and keeping `__proto__`.
  - [`native/tests/project_test.cpp`](../native/tests/project_test.cpp) builds it natively with strict warnings.
  - It builds for WebAssembly (176 KB, with `-fno-threadsafe-statics`) and opens the demo project identically there.
- **Not yet:**
  - The browser still opens projects with the TypeScript. Switching it would change the structural messages users see, so it waits for phase 9.
  - The typed C++ view of a project (structs for tracks, clips and so on) comes with phase 3, which edits it.
  - Opening the 11 MB demo projects takes about 0.4 s each natively. Number parsing and formatting and the generic value tree can be made faster.

## Phase 3 notes (2026-11-13)

- **Edits ported** ([`project_edit.hpp`](../native/include/xmp/project_edit.hpp)), each the C++ twin of a TypeScript function:
  - `toggleStep` and `expandSong`;
  - the sequence edits (`editSequence`, `appendNotes`, `quantizeNotes`, `resizeClip`, `duplicateClip`);
  - the performance (`editPerformance`, `editChain`, `deleteTrack`);
  - `editMix` and `setMidiDestination`;
  - samples (`manualSlices`, `installSample`) and drum kits (`applyDrumKit`, with its kit checks).
- **The rule:** like the TypeScript, every edit except `toggleStep` checks the whole project again (phase 2's `canonical`), so an edit can't leave a project the browser would refuse. The generic edits (`edit_sequence`, `edit_performance`, `edit_mix`) take a C++ function that changes the document, as the TypeScript ones take a callback.
- **Text cuts** (`name.slice(0, 30)`) are in UTF-16 units, as in JavaScript. Cutting a surrogate pair keeps its high surrogate alone, as JavaScript does.
- **The typed view** (`edit::view::Project`, `Track`, `Clip`, `Step`, `Scene`) reads the document in place, so the document stays the single source and its canonical order is never lost.
- **Checks:**
  - [`tests/parity/project-edit-parity.test.ts`](../tests/parity/project-edit-parity.test.ts) applies 24 random sequences of 60 edits to random projects, mostly well-formed and sometimes aimed at missing targets or invalid values. After every edit both implementations succeed or fail together and produce byte-identical projects. The TypeScript's own messages (not zod's) are identical. Every edit is exercised both ways (`expandSong` can't fail on a valid project).
  - Six deliberate faults each fail it: a default velocity, the copy-name cut, a missed scene clean-up, the quantize rounding, a track name and a choke default. The first version of the test missed two of them, until the generator had long clip names and mostly valid notes.
  - [`native/tests/project_edit_test.cpp`](../native/tests/project_edit_test.cpp) builds natively.
  - In WebAssembly (214 KB) a chain of five edits gives the same project as the TypeScript.
- **Moved to phase 4:** `setParameter` and `clearParameterSource` need the parameter registry and the machine definitions.
- **Edits in the browser's interface:** some edits are written inside the interface code (`apps/studio`) on a cloned project. The Live interface (phase 8) will use the C++ edits above and add its own where needed.

## Phase 4 notes (2026-11-13)

- **Machines** ([`machines.hpp`](../native/include/xmp/machines.hpp)):
  - the registry of `machines.ts`, with the pad sampler, the subtractive synth and the MIDI track;
  - their automatable parameters, defaults and state checks;
  - `get`, which returns a machine only for its own version and base (an absent machine is the pad sampler);
  - `instantiate`.
- **SDK machines** are JavaScript. Their definitions can be added (`machines().add`) so the registry lists their parameters as the browser does, but their own state checks run only in JavaScript. On the Live there are none yet.
- **Parameters** ([`parameters.hpp`](../native/include/xmp/parameters.hpp)):
  - `parameterRegistry`: master, the mix's pan, sends and effect parameters, track gains and machine parameters, in the TypeScript's order with the same names, defaults and steps;
  - `parameterSources`, `resolveParameter`, `parameterValue` and `machineParameter`;
  - `setParameter`, which snaps discrete machine parameters (MIDI channel) to their step and mirrors a base into the master gain, the track volume or the machine state, and `clearParameterSource`;
  - `smoothParameter`, `parameterSmoothingMs` and `advanceParameter`.
- **Checks:**
  - [`tests/parity/parameters-parity.test.ts`](../tests/parity/parameters-parity.test.ts) runs 20 random projects, some with an SDK-style machine, and over 5,000 queries and edits: the registry, sources, values, machine parameters, `instantiate`, smoothing and random parameter edits. Everything is identical (the TypeScript's own messages included), except smoothing, where the C library's `exp` may differ from JavaScript's in the last bit (within 1e-12).
  - Six deliberate faults each fail it. The discrete-step rounding was caught only after edits were biased toward machine parameters.
  - [`native/tests/parameters_test.cpp`](../native/tests/parameters_test.cpp) builds natively.
  - In WebAssembly (228 KB), the registry, every value and an edit match the demo project.
- **Not yet:** the browser, and the C++ sequencer's binding, still build the registry in TypeScript. Phase 5 has the C++ sequencer, transport and controls read the C++ project directly.

## Phase 5 notes (2026-11-13)

- **The sequencer on the C++ project** ([`play.hpp`](../native/include/xmp/play.hpp)): the layout the TypeScript binding built (UTF-16 IDs, tracks, step and sequence notes, parameter sources, lanes, locks and modulation), now built from the document. On top of it: `notesInWindow`, `timeline`, `eventsAtStep`, `parameterFrame`, and the parameter table the performance window uses.
- **The performance on the C++ project** ([`performance.hpp`](../native/include/xmp/performance.hpp)):
  - `Performance`, the C++ `PerformanceTransport`: scene and song mode, launches, clip changes, stop, live mute, solo and macro overrides, project and chain edits while playing, snapshots and releases;
  - `performance_controls`, `performance_values` (the evaluator) and `performance_window`.

  Everything a player needs to step through a project, with no TypeScript.
- **One behaviour change:** in the TypeScript too, simultaneous notes in a performance window are now ordered by plain code-unit ID instead of `localeCompare`, as the sequencer already orders them. Locale collation can't be reproduced outside a JavaScript runtime.
- **Checks:**
  - [`tests/parity/play-parity.test.ts`](../tests/parity/play-parity.test.ts) runs 24 random projects and about 4,000 queries (over 5,000 notes). Answers are byte-identical, except an LFO's `sin` in parameter frames (within 1e-12, as the sequencer parity test allows).
  - [`tests/parity/performance-play-parity.test.ts`](../tests/parity/performance-play-parity.test.ts) runs 16 random performances with MIDI routing, solos, macros, events, tempo maps, live controls, chain edits and clock jumps: about 2,500 operations, mostly window steps.
  - Eight deliberate faults each fail one of them (note pitch, note IDs, MIDI routing, window positions, tie order, song position, silenced gains, the silence check). Two were caught only after the generator added MIDI routing and long clock jumps.
  - [`native/tests/performance_test.cpp`](../native/tests/performance_test.cpp) builds natively.
  - In WebAssembly (353 KB, with a 1 MB stack), 32 windows of the demo project match the TypeScript exactly.
- **Next (phase 6):** rendering and exchange. The browser still calls the TypeScript versions; phase 9 moves it.

## Phase 6 notes (2026-11-13)

- **Files** ([`files.hpp`](../native/include/xmp/files.hpp)):
  - WAV: encoding 16-bit mono or stereo; decoding PCM16/24/32 and float32, mono or stereo, mixed to mono, with every check of `decodeSampleWav`;
  - Standard MIDI Files: `encodeMidi` and `decodeMidi`, including running status, velocity-0 note-offs, ignored events and the tempo map;
  - `exchangePlan` (the MIDI of a scene or a finite song, played through the performance) and `importMidiClip`.
- **The engine from a project** ([`voices.hpp`](../native/include/xmp/voices.hpp)): `prepareInstruments` and `editedPcm`, and the `VoiceRack` binding: tracks, pads, synth patches, routes, the mixer and its effects, parameter indices, and checked commands. SDK machines (JavaScript) are silent here.
- **Renders** ([`render.hpp`](../native/include/xmp/render.hpp)): `renderPerformance`, `renderSequence`, `renderInstrumentScene`, the original pad-sampler renderer (`prepareScene` with `renderPlan`), `renderProjectScene` and `renderExchange`.
- **Two TypeScript fixes found by the port:**
  - `renderSequence` sorted with an inconsistent comparator (two notes on one frame each sorted after the other), so the order depended on V8's sort. It now orders parameter changes before notes at the same frame, and otherwise keeps timeline order.
  - The JSON writer missed a rare case (decimal ties such as 2⁻²⁴, which JavaScript writes as `5.960464477539063e-8`). The JSON test now includes powers of two and dyadic fractions.
- **Checks:**
  - [`tests/parity/files-parity.test.ts`](../tests/parity/files-parity.test.ts) runs 400 WAV encodes, 400 decodes of random layouts (including invalid and damaged ones), and hand-made and damaged MIDI files. It also builds export plans in scene and song mode and imports clips. Bytes, documents, projects and messages are identical.
  - [`tests/parity/render-parity.test.ts`](../tests/parity/render-parity.test.ts) runs every renderer on random projects: performances in scene and song mode, sequences, instrument scenes, the pad-sampler renderer, whole-scene WAVs and MIDI-with-audio exports. Audio matches within 1e-5 (16-bit WAVs within one step). Note traces, transitions, MIDI events and files, snapshots and WAV headers are identical.
  - Six faults in the file code each fail the tests, and six of eight in the renders. The other two can't change the output: a mix strip's default pan (the parameter's base value always overrides it) and the order of gates and parameters at the same frame (they don't interact). Three faults were caught only after the tests gained hand-made MIDI files without a tempo, automation points between quarter steps, and an instrument render with a tail.
  - [`native/tests/render_test.cpp`](../native/tests/render_test.cpp) builds natively.
- **Not yet:** recording takes (`TakeRecorder`, the input path) waits for the owner's decision on the Live's audio inputs ([live-ux.md](live-ux.md)).

## Phase 7 notes (2026-11-13)

- **Opening the browser's files** ([`portable.hpp`](../native/include/xmp/portable.hpp)): `importPortable` in C++.
  - It opens plain projects, version 1 bundles (`project.xmp.json`) and version 2 songs (`.xmpsong`, with packaged float32 or float64 audio in base64 chunks).
  - It verifies SHA-256 as the browser does: each sample's hash, and the song's canonical project hash.
  - A song saved without its samples is refused, with the browser's message naming the missing samples (the Live has no sample library yet).
- **Playing in real time** ([`live_player.hpp`](../native/include/xmp/live_player.hpp)):
  - `ProjectPlayer` (main thread) steps the performance 100 ms ahead of the audio clock and turns each window into numeric commands.
  - `ProjectSound` (audio thread) applies them on their exact frames through the engine's allocation-free calls.
  - Stop cancels everything already scheduled and releases every voice; effect tails decay, as in the browser.
- **In the session** (`live_session.cpp`):
  - With `xmp/project.xmpsong` or `xmp/project.xmp.json` on the stick, the session opens it at start-up and prepares its sound before the audio thread starts.
  - Play and Stop play the project's song (when it has a chain) or its first scene.
  - The project mixes with the session's own sound, so the pads still play the kit over it.
  - The Live interface (phase 8) replaces this minimal control.
- **Checks:**
  - [`tests/parity/portable-parity.test.ts`](../tests/parity/portable-parity.test.ts) opens 240 files, intact and damaged: altered audio, hashes, base64 and versions, extra keys, renamed samples, foreign assets. Projects, refusals and XMP's own messages match the TypeScript's. Four deliberate faults each fail it.
  - [`native/tests/live_player_test.cpp`](../native/tests/live_player_test.cpp) plays a song from the top, the same song resumed from its saved position, and a scene through the real-time player, in 256-frame blocks. The output is identical, sample for sample, to `render_performance` offline. Stop cancels a queued note and releases every voice. Three of four deliberate faults fail it; the fourth only shortens the render blocks, which can't change the output. The clock fault was caught only once a resumed song was tested.
  - The session image builds with the Live's ARM compiler (`-Werror`). The emulator's new **project** run opens the browser's demo song from the stick, plays it with Play and stops it with Stop, with no xruns or dropped commands, sound on outputs 1–2 only, and within −12 dBFS. Nothing else in the emulator regressed.
- **Not yet:**
  - choosing among several projects on the stick (phase 8's Browse);
  - saving the project back;
  - MIDI out from MIDI tracks (authorization 5);
  - a song saved without its samples (it needs a sample library on the stick).

- **The button map is complete.** The codes from the owner's session 4 match, code for code, the MPC button numbers the open MPC mapper publishes (`references/repos/mpc-livexplore-libs/src/tkgl_midimapper.h`). So every printed label now has its code: Shift 31, Menu 7B, Main 34, Undo 43, Copy 7A, + 36, – 37, Tap Tempo 35, Note Repeat 0B, Full Level 27, 16 Level 28, Erase 09, and the transport row. They are recorded in `os/live-mk1/hardware.json` (`controller.map.labels`). Only the data wheel's press (6F) has not been pressed in a session yet.
- **The interface** ([`live_ui.hpp`](../native/include/xmp/live_ui.hpp)) is pure: the session passes in controller events and what the player is doing, and gets back actions. It draws to a `Canvas`, which on the Mac is a memory buffer. `native/tools/live_ui_preview.cpp` draws a project's screen to an image.
  - **Clips** (home): the eight tracks by up to sixteen scenes, and on the pads a 4×4 window of it (the selected track's four tracks by four scenes, the first at the top). Playing clips are emerald with a progress bar; a launch waiting for the bar blinks gold, a track about to stop blinks ruby.
  - **Play**: the pads play the selected track. A kit plays its 16 pads; a synth plays notes from C3, with – and + changing the octave. Full Level fixes the velocity.

  - Play plays the song when the project has a scene chain, otherwise the selected scene. Play Start plays the selected scene. Stop stops; Stop while stopped silences every voice.
  - The data wheel moves the selected scene; its press launches that scene.
- **The player** gained launches (`launch_clip`, `launch_scene`, on the next bar), `audible_step` (the step being heard, from the frames the steps were scheduled on), and live notes from the pads (`ProjectSound::play_live` and `release_live`, a new `note_off` command). The performance reports waiting launches (`queued`, `queued_scene`).
- **In the session:** with a project on the stick, the interface takes over the pads, buttons, data wheel, touchscreen and screen; the header keeps the five status lights, including the bridge light authorization 3 requires. Without a project the pattern screen works as before.
- **Checks:**

## Phase 8 notes, part 2 (2026-11-13)

- **Steps** (16 Level, or Menu + pad 15): the pads are sixteen steps of the selected clip, steps 1–4 on the top row, for one kit pad or one synth note. A pad turns its step on or off; Shift + pad chooses the pad or note to edit (the last one played in the Play view is chosen too); Erase + pad clears that pad's or note's steps. The data wheel pages through a 32- or 64-step clip. The step being heard is ringed in emerald.
- **Edits** ([`live_edit.hpp`](../native/include/xmp/live_edit.hpp)) change one clip of the open project in place. The browser's `toggleStep` copies the whole project, and a project's samples are megabytes of numbers, too slow to copy for every press on the Live. The results match the browser's: a kit step as `toggleStep` makes it (velocity 0.8, probability 1); a synth step with its own note, on a pad number free at that step, so a chord keeps the one-pad-per-step rule. Turning a synth note off also removes a sequence note of that pitch starting on that step.
- **Undo and redo** (Undo, Shift + Undo): each edit keeps the clip as it was, 64 deep.
- **While playing**, the player takes the edited clip from its next window (`ProjectPlayer::replace_clip`, `Performance::replace_clip`); the clip's id and length must not change, so the transport's tables still hold.
- **Saving:** two seconds after the last edit, once the music has stopped, the project is written to the stick as `xmp/project.xmpsong` (and at the end of the session), in the browser's own song format: [`portable::save_song`](../native/include/xmp/portable.hpp) is the C++ port of `exportSong`, byte for byte (tests/parity/portable-parity.test.ts), with the audio as base64 float32 chunks. It takes 37 ms on the Mac for Night Shift; the first version wrote every sample as a JSON number (`project.xmp.json`, 5 MB), which took 2.6 s on the Mac and about 94 s in the emulator, where it stalled the controls for seconds at a time. A low-priority thread still makes the file from a copy, so the controls and screen never wait. The first save of a session keeps the song it replaces as `project.previous.xmpsong`. When both `project.xmpsong` and `project.xmp.json` are on the stick, the newer opens.
- **Checks:**
  - `native/tests/live_ui_test.cpp` now also covers the Steps view, every edit, undo and redo (and their bound), the edited project reopening, an edit made while playing (the sound is unchanged before the edited step and changes from it), and the Steps drawing. Of twelve deliberate faults, eleven fail it; the twelfth skips the player's own copy of the clip, which it never reads for notes (the performance's copy is the one played), so it can't change the output.
  - The emulator's project run edits a step of Night Shift's bass in the Steps view, undoes and redoes it, and checks that the saved `project.xmpsong` opens in the browser's core with the step.
  - Emulator result (run `session-vm-yXFdjN`): every interface check passes (Play, Stop, a clip alone, a launch at the bar, Shift + Main, the wheel's scene launch, the step edit, undo, redo, the save, and the saved file reopening with the edit), with sound on outputs 1–2 only, under −12 dBFS, and no dropped commands. Two checks fail:
    - `screenShowsClips`: the emulator's screenshot is QEMU's 640×480 default display, not the Live's framebuffer, so every screen check in every run fails the same way (it did before phase 8 too). The screen is checked by the native drawing tests and `live_ui_preview` instead.
    - `noXruns`: 7 xruns, none while music played (the captured audio has no gaps). They fall in the silent stretch while the 5 MB project was saved (84 s under the emulator), most likely because QEMU runs all four emulated cores on one host thread, so the saving thread takes time from the audio core; on the Live the audio core is a separate, isolated core. The session now logs each xrun with whether it was playing or saving, so a real session will show where any happen.

## Phase 8 notes, part 3 (2026-11-14)

- **Rec** records a take into the selected empty slot of a kit or synth track, and opens the Play view so the pads play that track. Stopped, it starts the slot's scene and its first bar counts in; playing, the take starts on the next bar. A hit up to half a step before the take is its first step. Rec again ends the take: its clip is one, two or four bars (16, 32 or 64 steps), pressing up to half a step late doesn't add a bar, and a take ends by itself after four bars. Stop ends it too. The new clip ("Take N", an id no clip in the project has) goes into the slot and plays from the next bar.
- **Overdub** records onto the clip the selected track plays: each hit lands where it was played in the loop, a kit hit at once, a synth note when it is let go (with its length). Overdub again, or the clip stopping, ends it.
- **Quantizing:** hits go to the nearest step; one just before the end lands on step 1. A kit hit on a step its pad already has keeps the louder velocity; a synth note of a pitch already on that step plays once. Synth notes keep their length in quarter steps (at least a quarter).
- **Undo** takes back a whole take (the clip and the slot), and an overdub pass from its first hit. A take or its undo changes the project's clips and scenes, so the player takes the whole project (`ProjectPlayer::set_project`) and keeps playing where it is.
- **The player keeps a lean copy:** the project without its samples' audio, which playback never reads (only ProjectSound and the offline renders do). Starting to play, a take and an undo copy kilobytes instead of megabytes. Playback is still identical to the offline render, sample for sample.
- **Checks:** `native/tests/live_ui_test.cpp` adds take lengths, quantizing, new clips and their undo, the whole Rec and Overdub flow (count-in, early hits, held notes, the late press, the four-bar limit, Stop, a press on the bar line, an overdub hit before its clip's start), the player taking a take while playing, and the REC display. Seventeen deliberate faults all fail it. The emulator's project run records a one-bar take on Night Shift's lead from stopped, overdubs a note onto it and checks the saved project.
- **Emulator (2026-11-14):** every Rec check passed except `overdubbed`. The save of the Steps edit was still writing (the 94 s noted under part 2) and stalled the controls for seconds, so Rec was handled 2.3 s late and the take had not started when Overdub was pressed. ## Phase 9 notes, part 5: where the TypeScript stands (2026-11-14)

- **Steps 1–4 are done.** The browser opens and saves every project file, makes every project edit, reads and sets every parameter, reads and writes WAV and MIDI files, renders, and plays (both with and without a performance or mix) through the C++ core in WebAssembly. The sequencer panel's parameter frames moved with this note.
- **Still TypeScript at run time, by design:** recording takes (`TakeRecorder`, `NoteTake`, `AutomationTake`, `PerformanceTake`, `NoteRepeat`), the SDK's machine registry (plugin machines are JavaScript), Web MIDI routing, `ProjectSession` (the interface's undo history), the audio worklet's `VoiceRack` (itself a wrapper of the C++ engine's WebAssembly) and the instrument palette it is sent (`prepareInstruments`), the demo song, the schemas the interface checks form input with, and small helpers it calls synchronously and often (groove, swing and tempo arithmetic, `sceneLength`, `clipFor`, MIDI destinations, effect defaults, `hashSample` for relinking).
- **Step 5, deleting the TypeScript copies of what moved, has not been done.** The plan sets it for "once the browser has run on C++ for a while": until then, the TypeScript copies are what the parity suites and the new `tests/project-io`, `edits`, `media` and `playback` tests compare the C++ against, and deleting them first means recording golden expectations so those tests keep checking something. The copies are no longer called by the browser.
- **Known slowdown, deferred by the owner:** playback windows through the core take 5.6 ms against the TypeScript's 1.4 ms (transport getters 14 µs against 0.2 µs). It is a to-do in [future.md](future.md).

## Phase 9 notes, part 6: the engine originals retired (2026-11-14)

- **Retired:** the original TypeScript engine rack (`reference-rack.ts`), sequencer (`reference-sequencer.ts`), transport (`reference-transport.ts`) and performance controls (`reference-controls.ts`). Nothing but their parity tests reached them since the browser moved to the C++ engines.
- **Golden expectations:** before deleting them, their five tests ran once more comparing the C++ (as WebAssembly, so the same bits on every machine) with the originals, and recorded a SHA-256 fingerprint of every C++ result while they matched ([`tests/golden.ts`](../tests/golden.ts), [`tests/golden.json`](../tests/golden.json)): 14 fingerprints over the engine's audio, MIDI, voice counts and meters; the sequencer's groove, notes, timelines, step events and parameter frames; the transport's results and state after every operation; and the controls' and parameter values' results. The tests now drive the same random scripts and require the same fingerprints. The engine's audio is rounded to 1e-6 first, since the SDK's example machines run in JavaScript, whose Math may change in the last bit between Node versions. `XMP_GOLDEN=record` rewrites them, for a deliberate change only.
- **Then the renderers and file code** (same day): `exchange.ts`, `offline.ts`, `sequence-render.ts` and `performance-render.ts` are gone too. Their last callers, the command-line tools (`export-project`, the lab agent, the demo song), the guest OS and the acceptance steps, now use the WebAssembly core (`edits.ts`), which gained `prepareScene` (the scene plan the native song renderer reads), `renderSequence`, `renderScenePlan`, a full `renderInstrumentScene` result (its notes, refusals and WAV) and each render's command count. `saveExport` moved to `export-sink.ts`. The native parity suites for files and renders now compare the native C++ build with the WebAssembly one (same source, two compilers); `tests/media.test.ts`, `tests/playback.test.ts` (the scheduled commands) and the new `tests/renders.test.ts` check fingerprints recorded while the core matched the TypeScript. Renders return their scheduled commands again (the acceptance steps replay them into the worklet). `bdd:test` passes on the core. The first `bdd:implemented` run found three failures from this change (a version check still expecting 6, and two steps reading the commands), now fixed but not yet rerun; its other three failures (`npm run check` in a clean checkout missing `artifacts/demo/night-shift.xmpsong`, and an SDK build that saw sources change mid-run) need a separate look.
- **Then the mixer** (same day): `mix-dsp.ts`, the original TypeScript mixer and effects, is gone. The engine's WebAssembly now also gives JavaScript the C++ engine's own effects and mixers as standalone objects, and [`mixer.ts`](../packages/core/src/mixer.ts) wraps them with the old API (`EffectProcessor`, `StereoMixer`, `panGains`). `tests/mix.test.ts` and the mix acceptance steps run on it. Before the deletion, `tests/mixer.test.ts` compared the two on 60 random effects (every kind, sync, bypass, automated values, a clear midway) and 24 random mixes (pans, sends, inserts, returns, tempo changes, meters, the clock): every sample within 1e-9. It now checks the fingerprints recorded then.
- **Still TypeScript:** the project schemas and helpers in `index.ts`, the instrument palette (`instruments.ts`, which the audio worklet uses), the performance and sequencer helpers the interface calls synchronously (`performance.ts`, `sequencer.ts`), recording takes, and the schemas the interface checks input with.
