# XMP instrument design: learning from Roger Linn

Researched on November 8, 2026. This is a design input for XMP's existing twelve-phase plan. The numbered decisions below are our interpretation and product requirements, not instructions, endorsement or specifications supplied by Roger Linn. They do not change the owner's hardware boundary or resolve the missing external specification.

## What Linn contributed, and how he worked

Linn was a musician and product/interface designer as well as a self-taught engineer. For the MPC60, he describes creating the functional specification, user interface and LCD content. Alan Trimble developed software with Linn and others; David Cockerell designed its sound chip; Akai's Tokyo team produced circuit boards and mechanics to the specification. The MPC60 appeared in 1988. Treat this as a collaboration, rather than crediting one person for the entire machine. [Linn's own account, MPC questions](https://www.rogerlinndesign.com/about/roger-faq).

The LM-1's real-time entry, LinnDrum's refinement, Linn 9000's ambitious integration, MPC60/MPC3000 workflows, AdrenaLinn's synchronized processing, Tempest's performance controls and LinnStrument's expression represent different problems and solutions. Their common thread is making musical actions playable. We are adopting principles, not emulating their circuits or copying their interfaces.

Linn also describes the Linn 9000's complexity and reliability problems, the scale of the abandoned LinnDrum II effort, and the value of the old MPC Help button. Those are useful counterweights to adding features indiscriminately. [His FAQ and June 2026 essay](https://www.rogerlinndesign.com/about/roger-faq) (S01).

### Musical timing contract

For internal odd-step delay `d`, the first-sixteenth share of the pair is `50 + 50d` percent. This follows directly from the existing two-step timing model: `(1 + d) / 2`. No project schema migration is necessary. Display rounding never changes stored timing: the Triplet button stores `1/3`, not a value reconstructed from the rounded label `66.7%`.

At 120 BPM and 48 kHz, the second sixteenth starts at frame 6000 for straight timing, 7440 for 62%, 8000 for exact triplet, and 9000 for 75%. Every bar still begins 96000 frames after the previous one. These independent expectations are checked against actual exported PCM, not just a UI string. Existing stored `0.5` remains 75% and plays at exactly the previous timestamp.

### Interaction contract

Help/F1 opens a nonmodal explanation for the last focused musical control. Escape or Close returns focus to that control if it still exists, otherwise the Help button. Help has no project or audio-engine reference. Pad/transport shortcuts inside its panel do not reach the music view. The rest of the instrument remains usable; opening help itself does not pause or restart transport. An engine tick or UI redraw must not turn a close action into an edit on another track.

Primary views will emphasize Play, Record/Overdub, Undo, sound choice and performance. Detailed sequencing, routing and development tools remain accessible. Names such as velocity and swing explain the musical result; exact units, parameter IDs and engineering ranges remain available where precision matters. A first-time workflow must be tested with musicians; passing deterministic contracts alone does not prove that an interface is easy to learn.

### Expression and platform contract

The future internal event model needs stable note identity, source timestamps, velocity and declared optional pressure/pitch/timbre dimensions. Voice-scoped updates must respect the source and instrument capability declarations. A keyboard, a pressure pad and a multidimensional controller must not be treated as interchangeable sensors. Unsupported dimensions are shown as unavailable and cannot be fabricated from mouse position or a generic vendor ID.

S05 is a historical 2016 discussion, not the current MIDI/MPE conformance specification. Standards/version selection, channel/voice allocation, recorded expression storage and external-fixture qualification need a separate P08/P09 implementation decision. The new acceptance cases define internal ownership and fallback behavior; they do not claim MPE compatibility. No external MIDI access is enabled by this work.

## Verification and limits

Run `npm run bdd:design` for nine expanded implemented contracts covering musical ratios, compatibility, invalid input, real Studio event handlers, undo, contextual help and focus recovery. The UI cases execute in Happy DOM with audio/storage mocked and a constructor that fails if audio-device creation is attempted. Their nested Vitest JSON is retained in the Gherkin evidence. This validates event/state behavior, not browser layout, sound latency or physical pad response.

Run `npm run bdd:plan` and `npm run bdd:docs:check` for the planned requirements. Added P05–P11 scenarios remain `@planned`; they cannot pass from a document or simulator result. The OS must later run shared contracts inside its booted image, and a specifically authorized deployed target must supply its own control and physical-audio evidence over the reviewed USB test route.

The Force remains passive host-inventory only. No Akai connection is needed for this increment. Physical P04 loopback remains pending at the owner's request. XMP includes no vendor sound set, copied graphics or implied Roger Linn/Akai affiliation.

The source catalog is [references/design-sources.json](../references/design-sources.json). It records URLs and reviewed sections without archiving interview text. The existing Git reference watcher remains responsible for repositories; it does not pretend to monitor changing interview pages.
