# MPC One family: port and qualification plan

The owner has a Live Mk1, so that unit remains the physical regression reference. Original MPC One and One+ are priority expansion targets. Work on their source profiles, input abstraction, UI and emulation can proceed without buying hardware. Physical compatibility requires participating owners or loan units; the Live cannot prove One audio, controller, boot or recovery behavior. One G2 is a separate later platform effort. [Canonical status and source evidence](../compatibility.md).

## Implementation order

1. **Separate shared workstation code from model adapters.** Keep sequencing, projects, SDK and DSP shared. Define source-level board profiles for display rotation, control layout, audio backend/channel maps and storage rules. Keep the current Live adapter and its fail-closed guards intact. Never select a generic fallback when the board is unknown.
2. **Design the original One adapter from pinned primary sources.** ACVA has an onboard `acva-audio` codec, not the Live's `09e8:203b` USB audio card. Review the kernel driver's codec initialization, mute/reset/power behavior, playback/capture channel map and gain path. Establish controller identity/startup bytes and model-specific button/Q-Link maps from authorized evidence; do not infer them from the Live. Use the established −12 dBFS playback ceiling as a conservative design constraint, subject to the tester's explicit authorization.
3. **Treat One+ separately where hardware differs.** Review ACVA2 device-tree deltas, controls, codec and radio firmware/licence requirements. Share implementation only where the sources and tests prove parity. The proposed 3.10.1 owner-local runtime route must be audited against each model; same updater membership alone does not qualify it.
4. **Design installation and recovery before enabling builds.** Establish exact unit/board/revision, official starting firmware, bootloader, model-specific update-mode entry, readable partition capacity and verified stock recovery. Preserve rootfs-only/bootloader-untouched design where demonstrably applicable. No Live flash, bridge or SSH wrapper may contact a One. Record device-specific owner authorization before developing or running any physical tool route.
5. **Exercise host and emulator refusals.** Test wrong board, mixed identities, Force, wrong firmware, damaged hashes, missing capacity, oversized images, unsupported storage, interrupted image promotion and fallback. Use board fixtures for adapters; label generic ARM VM tests accurately. None proves onboard codec or physical control behavior.
6. **Qualify each real model and revision.** Have an explicitly authorized owner first verify stock recovery, then rehearse first installation, no-stick stock handover, update, previous-image fallback and full return to stock. Collect model-specific UI/touch/pads/knobs, playback/capture/channel, persistence, storage-boundary, mains/power-off and performance evidence bound to exact source/image hashes. Run the launch workload and soak on each promised model. Review sanitized results before changing the canonical status or enabling installation.
7. **Investigate G2 separately.** Confirm board IDs, CPU ABI, kernel/toolchain, driver/control architecture and owner-local firmware/runtime route from primary sources. Do not assign ACVA3, an SoC or an ABI based on third-party descriptions. A Gen 1 3.10.1 image is never a G2 test image.

The SDK should let other developers build original instruments, UI and workflows on the shared foundation. Model porting should not force every app developer to solve boot, storage, controls and audio plumbing again. Document adapter contracts and model-specific capabilities when implemented; do not present the current SDK as a working One hardware SDK.
